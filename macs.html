Does a team of AI agents write more original code than one assistant?

MACS is a multi-agent coding studio and a measuring instrument for it. I built the system, designed a pre-registered experiment, ran 12,909 sessions on a GPU cluster and analysed the results. Supervised by Prof. Solomon S. Oyelere.

The question

A single AI coding assistant tends to give the same kind of answer each time. A team of agents with different roles might explore more ideas. But "more creative" is easy to claim and hard to measure, so most of this project is about measuring it properly.

I asked two things. Does a role-based agent team produce more varied and original correct code than a single AI tutor? And do automatic creativity scores agree with human judgement?

The system

The studio has four role agents and a Facilitator. They work on a programming task alongside simulated learners, adapted from the ASTRA tutoring framework.

  • Innovator proposes approaches. Engineer writes the code. Verifier runs the tests. Critic challenges the result.
  • Facilitator watches the session using code embeddings (UniXcoder). When the team's ideas start to converge, it steps in with one of four interventions to push them somewhere new.
  • Every model reply is cached by a hash of the request, so any run can be replayed exactly.
  • Every turn is written to a JSONL trace that is checked against a schema.
  • Generated code runs in a sandbox with no network and limits on CPU time and memory.

The codebase is a Python package of about 45 modules with 135 automated tests, and a Streamlit dashboard for running and checking the study.

How I measure creativity

Each solution is turned into a 26-number description of its code structure, taken from its abstract syntax tree. Three scores come from that.

  • Diversity. Solutions in a session are clustered into "solution families". More families means the session explored more distinct approaches.
  • Novelty. How far a solution sits from its five nearest neighbours among 100 ordinary reference solutions, as a z-score.
  • Correct and novel. A solution counts only if it passes held-out tests and is more novel than 90% of the reference set.

I repeated the analysis with neural code embeddings as a second representation, to check the results did not depend on one way of describing code.

The experiment

I pre-registered the design, hypotheses and decision rules before the main run, and logged every later change as a dated amendment.

  • 11 conditions, including a single tutor, the studio, the studio with the Facilitator switched off, a tutor given the studio's token budget, and one prompt that asks for five different approaches.
  • 27 tasks: 24 main tasks drawn from MBPP, HumanEval and heuristic design problems, plus 3 EvoEval tasks to check for training-data contamination.
  • 6 seeds per cell, across 8 open-weight models: Qwen, Gemma, Llama, Granite and gpt-oss families.
  • Run as self-resubmitting Slurm jobs on NVIDIA A100 GPUs.

The analysis uses a mixed model per model with planned contrasts, 95% confidence intervals and Holm correction, then a random-effects meta-analysis across all eight models.

Results

Twice as many correct and novel solutions

Share of sessions producing a solution that passes held-out tests and is novel.

  • The studio explores more. On the main model it found 2.76 more solution families than the single tutor (95% CI 2.36 to 3.15). The effect was positive on all 8 models, with a pooled estimate of +1.66.
  • More solutions that are both correct and novel. The rate rose from 0.30 to 0.65.
  • It is not just extra compute. A tutor given the same token budget still trailed the studio by 2.63 families.
  • The Facilitator helps a little. Switching it on added 0.25 families on the main model and 0.19 pooled, positive on all 8 models.

What did not go as hoped

One good prompt matched the whole team. A single prompt asking for five different approaches produced about the same diversity as the studio, at roughly a quarter of the tokens. That is the most useful practical finding, and it argues against building a team when a prompt will do.
  • That prompt only worked on larger models. One small model produced no scoreable code with it, and another lost 0.41 in pass rate.
  • Human ratings agreed with my novelty score in direction but only weakly (ρ = 0.19).
  • The solution-family clustering did not reach the agreement target I had pre-registered.
  • When I used LLMs as judges, a small judge model mostly followed the order items were shown in. Larger judges were consistent (Fleiss' κ = 0.88).

I report these alongside the positive results. A measurement project is only useful if it says where the measurement is weak.

Reproducing it

The repository contains every analysed trace, the reference sets, the response cache and all results. Anyone can rescore everything with one command, without a GPU or a model server, and get the same files.
